# Module map: app/agent

The [architecture](../ARCHITECTURE.md) explains the layers; each row below says what one file is and does.

## `app/agent/`

| File | What it is |
| ---- | ---------- |
| `app/agent/artifacts.js` | The agent's `artifact` tool (HarnessV4_Artifacts_Plan E18), the same for both engines: a page that lives outside the chat, in the developer's Artifacts list under an address of its own, every version kept. `ARTIFACT_TOOL` (`ARTIFACT_ACTIONS`: guide, publish, read, list, read_db, write_db; no delete) and `artifactCall(input, at, store)`; a publish over a version its session has not read is refused. Also `ARTIFACT_GUIDE`, `artifactsMakeHere`, `ARTIFACTS_OFF`, `publishFolderApp`, `pinnedFor`. |
| `app/agent/attach.js` | What the main agent hands its sub-agent with a launch or a follow-up (`attach`, the owner's of 11-17): `attachments(items, from)` reads each path once on its side, judged as its own read (`readJudge`: read rules, fence), or `picture N` of the person's this turn (`openingPictures`, then steers; none once taken up from the archive); kept whoever asks: the data folder, `.git`, secrets, credentials, private keys; sniffed by bytes, redacted, capped (`ATTACH_LIMITS`), refused whole. `fileBlocks`. |
| `app/agent/beside-tool.js` | The main agent's `team` tool (team_v2_plan §5.5), one of Filament's own for both engines: `BESIDE_TOOL` (`BESIDE_ACTIONS` send, status, note) sends a team beside the chat — a lead that reads the whole chat, with workers of its own, in a chat of their own (app/teams-beside.js) — and says how the teams beside it stand, never their results. `besideAtOf`, `besideCall`, `leadStep`, `BESIDE_TEAM`, `BESIDE_OFF`, `BESIDE_SWITCHED_OFF`. Offered to a harness chat's own agent while `loop.tools.team` is on. |
| `app/agent/browser-tool.js` | The `browser` tool (HarnessV4_Browser_Plan BR2): `BROWSER_TOOL`, one tool whose `action` looks (navigate, snapshot, screenshot, resize, …) or acts (click, type, press, select, evaluate). `browserOffered` offers it by the session's `plugins.browser` alone, so its bytes never move with the desktop app. `browserGate`: looking runs in every mode; acting is refused read-only (`BROWSER_READ_ONLY`), runs in Full access, and in Edit mode asks once per site (`browserQuestion`, `actingSite`). |
| `app/agent/chat-always.js` | "Always allow in this chat" (d-allow): the commands a chat keeps on its meta (`alwaysRun`, `ALWAYS_MAX` at most), for its own seat alone. `keepsOf`: what a press keeps of a command — each part that neither only reads nor is a `cd` that stays put; never an install, a one-way step, a redirect or a substitution. `keepsFor`: the offer an ask carries. `keptFor`: the kept commands a command runs on, read as a grant reads (grants.js, exact entries). `keptNow`, `withKept`, `withoutKept`, `alwaysWords`. |
| `app/agent/check.js` | The words of Filament's own run of a worker's check (HarnessV3-TaskGraph-v2 TG2-D45), pure; the registry runs the commands (subagents.js). `checkWords` (the report's: passed, failed after `CHECK_RETURNS` returns, stopped, or not run), `bounceText` (what a worker sent back reads), `failedRun`, `checkRuled`, `taskRuled`, `checkingWords`, `sentBackWords`; for the folder's check after a lead's apply (TG2-D55) `folderRuled`, `folderTail`, `undoneText`, `undoneNote`, `stuckText`, `waitingText`. |
| `app/agent/come-back.js` | The agent's `come_back` tool, as Claude Code's scheduled wakeup: Filament starts a turn of the agent's in its chat once the time it set has passed, with the note it left. `COME_BACK_TOOL`, `comeBackCall(input, at)` (one per chat, a new one replacing it, through hands.js `comeBackLater`), `cancelByPerson` (the page's Cancel), `COME_BACK`, `COME_BACK_OFF`, `NO_COME_BACK`. Offered to a harness chat's own agent alone; the person's Stop and Filament's restart drop it. |
| `app/agent/commands.js` | A coding agent's long command in the background (HarnessV4_Background_Plan E34): `BACKGROUND_COMMAND_TOOL` and `createBackgroundCommands({ registry, log })`. Filament runs it, the agent goes on, and its end (`endText`, `tailOf`) comes back whole beside its next tool call's result, else in a turn Filament sends the chat; never sealed. `commandRow`, `commandsOf`, `allCommands` (the page's running commands), `runningRecord`, `tellStoppedCommands` (at start), `stopByPerson`. |
| `app/agent/craft-tool.js` | The crafter chat's `craft` tool, one for both engines, offered in a crafter chat alone (opened by `/craft <words>`): `CRAFT_TOOL` with `CRAFT_ACTIONS` — make names the skill the chat crafts, books adds files to its library, find and read look in it, write puts a file in its folder, look shows it. `craftAtOf(deps, chain)` (null outside a crafter chat), `craftCall(input, at)`, `CRAFT_NAME`, `CRAFT_OFF`. A SKILL.md written keeps the lines added from memory (skill-from-memory.js). |
| `app/agent/envelopes.js` | Envelopes' words (HarnessV4_Envelopes_Plan), pure: another agent's result that lands while an agent works reaches it sealed, one line in its sender's words, until it opens it. `subjectOf` (the `Subject:` line, `SUBJECT_CHARS`), `envelopeLine`, `sealedListText` (a turn's start, after a compaction), `sealedReminder` (a turn's end), `openedText`, `envelopeAnswer`, `pictureAnswer` (the envelope tool's answer to `{ picture }`). The registry (subagents.js re-exports four) and the loop both read them. |
| `app/agent/environment.js` | The loop's Environment section (HarnessV3-SystemPrompt SP-D2/D3): the clock and zone, the system, the shell the bash tool really runs and its PATH, Filament itself, the folder's git state and how the project runs its checks. `captureEnvironment` (`clockOf`, `systemOf`, `shFlavor`, `pathToolsOf`, `keptPathTools`, `harnessCommand`, `gitFactsOf`, `projectFactsOf`), `cachedCapture`, `storedEnvironment`, `createEnvironmentKeeper` (frozen per session), `environmentText`, `environmentSummary`. |
| `app/agent/flow-tool.js` | The main agent's `flow` tool (HarnessV4_OneAgent_Plan OA3), one of Filament's own for both engines: it drafts a flow of the person's agents and teams once the person asks with `/flow`, edits its own draft and reads how the chat's flows stand; Start stays the person's. On a flow started In place it drives the boxes (`box`, `stop`); `offer` puts a Run as a flow button under a reply. `FLOW_TOOL`, `FLOW_ACTIONS`, `FLOW_BOX_DOES`, `flowAtOf`, `flowCall`, `FLOW_NAME`, `FLOW_OFF`, `FLOW_SWITCHED_OFF`. |
| `app/agent/grants.js` | What a team's brief lets its worker run with nobody's answer (TG2-D44), pure: its `check` (up to `CHECK_MAX`, run by Filament once the worker reports) and `may_run`, granted in the worker's own worktree. A grant covers its command as written or with more words after — an `exact` one (a chat's always-allow) only itself; never an install, a redirect, a substitution. `grantsOf`, `grantsProblem`, `grantsRefusal`, `grantFor`, `grantWords`, `launchWords`, `grantsNote`, `withCardRuns`, `withTeamCheck`. |
| `app/agent/graph-notes.js` | What the planner keeps behind its task graph (E33): the tasks tool's `keep`, `read` and `find`, which the graph runner hands here. `createGraphNotes({ notes, fileFrom, pictureFrom })` → `{ on, call, hits, noteText, kept }`: a keep puts a note, files and a picture's code behind a task or the graph (services/task-notes.js); a read lists what is kept or reads one in parts (`partOf`); `hits`, a find's lines. `graphNoteSources` says where a file may come from and finds a picture by its name. |
| `app/agent/held-launch.js` | Launches held for the person's yes while Parallelize tasks is off (the owner's of 11-14): `createHolds(…)`, each chat's card for sub-agents that change files, answered by the person or by itself after `HOLD_MS` (Accept wherever each would work, a launch with no model known staying the agent's; one card a turn, `drop` with its chat), each answer told to the agent; Always accept in this chat said too (`ALWAYS_WORDS`). `heldWords`, `answerWords`, `ONE_AT_A_TIME_WORDS`. |
| `app/agent/graph-runner.js` | The runner behind each session's task graph (HarnessV3-TaskGraph G2, G3): `createGraphRunner(…)`, one per process. Every change to a graph (`meta.graph`) goes through it, and out on the bus (topic `graph`) where a page draws it. It starts tasks as their needs finish, runs the reviews that wait, merges a writer's change only on an apply, and tells the planner each end, with what it is (`about`) for the wake's words; the side card's Accept and Ignore wake it. `MERGE_RETRY_MS`. |
| `app/agent/hooks.js` | Session hooks (HarnessV2 §5.6): commands named in the settings document, run in the project folder at seven moments — `prompt-submit`, `pre-compact`, `subagent-end`, `pre-tool`, `post-tool`, `turn-end`, `session-start`. The event goes as JSON on stdin; a JSON verdict on stdout wins, else exit 0 allows. `createLoopHooks`, `runHook`, `parseHookOutput`, `hookLabel`, `describeHook`. A plugin's hook speaks Claude's dialect (core/plugin-hooks.js). Each run is audited and drawn as a `hook` card. |
| `app/agent/instructions.js` | Instructions (HarnessV2 §5.6): the person's own files, the project's files from the chat's folder up to the repository's top, and the session's text, one block at the end of the loop's system prompt (`instructionsBlock`), kept as the chat's prompt was written until its next compaction (`kept`); one changed since is a note on the next message (`instructionsChanged`). A folder below is told its files when the agent first works there (`folderInstructions`). Also `foldersUp`, `yourFilesCheck`. |
| `app/agent/looks.js` | A lead's looks at its running workers (HarnessV3-TaskGraph-v2 §12): each one's plan, what it has done so far, and every round since the last look whole, never its thinking — due at once on a sign, else at the developer's pace. `newMark`, `noted`, `createLooks` (when a look is due, its words), `patchWords`, `wroteWords`; the lead's conversation keeps the newest look whole (`tidyLooks`, `withoutLooks`, `holdsLook`, `isLook`). The session's agent gets the same looks at its sub-agents. |
| `app/agent/loop.js` | The D1 agent loop (plan WP-F): `runAgentTurn(args)`, one model with Filament's hands behind `agent/<model>` — a model call a round, tools run in order. `agent` calls and reads run side by side (`READS_AT_ONCE`); a permission or question pauses it; a message typed meanwhile arrives between rounds; a busy provider is retried; a cut reply goes on (`cutReply`); a written file's errors, from its language server, ride the result and its card (`errorsAfter`). Also the relay heads, `WRITING_HANDS`. |
| `app/agent/link-guard.js` | What the gate asks about on Windows in every mode, Full access too, past any rule or grant (11-08): a folder's link made outside the chat's folder leading into it, and a recursive delete of a folder holding one leading out (a capped walk). Read from the command's syntax with the rules' `shellWords`, through `cmd /c`, `powershell -Command` and `bash -c`, from where each `cd` leaves it. `linkRisk`, `linkWords`, `linkOutOf`, `segmentsOf`. |
| `app/agent/lsp-tool.js` | The agent's `lsp` tool: `LSP_TOOL` (`LSP_ACTIONS`: definition, type_definition, implementation, references, hover, symbols, workspace_symbols, diagnostics), after the hands in every loop agent's set, run in every mode. `runLsp` picks the file's server (`serverFor`), holds it from turn.js's pool, and answers with places relative to the folder and their lines, a hover, symbols or problems — or why none, in words. `projectSymbols`: the project's names an `@#` lists, kept to its files. |
| `app/agent/mcp-resources.js` | The resources of the session's MCP servers, as Claude Code reaches them: `MCP_RESOURCES_TOOL` (`mcp_resources`), one tool that only reads — `list` names what each server offers (resources and templates, at most `RESOURCES_LIST_MAX`), `read` gives one's content — and `resourcesAnswer(input, servers, …)`, redacted and cut as a tool's result. turn.js offers it after the servers' own tools where a connected server says `capabilities.resources`. MCP's prompts stay out: the person's to pick. |
| `app/agent/prefix.js` | What a chat's loop sends ahead of its history, as a print: `buildPrint()` (the build's prompt and tools, every one a loop chat may be sent), `loopPrint(doc)` (that, and the chat's MCP servers, tools off, skills, web and browser), `agentPrint(doc)` (a coding agent's: `buildAgentTools`, its standing words, its MCP servers) and `printChanges(was, now)`, in words. The session keeps the print it sent (`prefixSent`) and weighs the next message against it. |
| `app/agent/prompt.js` | The loop's system prompt and tool descriptions as frozen constants (plan §4.4) under one `PROMPT_VERSION`, stamped on every agent-turn record so each change can be measured on replay-compare. `PROMPT`, `TOOL_TEXT`, `TEAM_TEXT`, `PERMISSION_MODES`, `LEAD_HANDS` and `systemPromptFor(…)`: the sections, the operator's overlay, and the prompts of a sub-agent, a team's lead and a worker. Project rules come through the briefing and the mode through the gate, so the cached prefix holds. |
| `app/agent/remote-agents.js` | A sub-agent on another machine, the `agent` tool's `machine`: `place` (a folder named, else its own copy, `copyPlace`, `sendCopy` asking once a project per machine, `sendsKept`, `repoKeyOf`; else the clone), `takeBack` (its copy's change), `placeForPerson`, `placesFor` (Run on), `whereWords`, `turn` (each message to its chat there, its mode and model, `modelThere`, its words streamed; its asks to the person here; a silent machine: `unreachableWords`, `stopOwed`). `machinesText`, `modelsText`. |
| `app/agent/remote-commands.js` | A background command on another machine: `createRemoteCommands` `start`s bash_background's or background_command's `machine` there through its exec route as a background shell here (hands.js `keepRemoteShell`). This chat's mode judges it there, sent where that machine `takes` exec-mode, an ask rule here first; asks go on this chat's card (`thereForm`), answered by a press alone (`thereReply`). A dropped stream is read again by its id while it runs there (`LOST_AFTER_MS`); a stop is sent there. |
| `app/agent/roster-words.js` | The sentences of a lead's prompt and tools that name its team's members (HarnessV4_Tasks E15 step 6): `SHIPPED_ROSTER_WORDS`, the words for the four members every shipped team has (scout, builder, tester, reviewer), and `rosterWords(members)` for any other list — one line per member: its tag, what its card is good for, what its work does to the files — frozen per list under `rosterKey(members)`. prompt.js and tools.js put each part where its sentence stands. |
| `app/agent/rules.js` | `loop.rules`, judged before the permission gate: a rule names a tool and a glob over the call's subject (`subjectsOf`: a command and each of its parts, a path, a pattern, a URL, a browser page). `deny` refuses, `review` asks with a second look, `ask` asks, `allow` runs but never above read-only; first match wins. A command is judged as written and as its shell reads it (`commandSegments`, `shellWords`, `plainSpellings`, `WRAPPERS`). `ruleFor`, `rulesFrom`, `learnedRuleFor`, `readRules`. |
| `app/agent/skills.js` | Skills (HarnessV2 §5.6): `SKILL.md` files from Library › Skills and the plugins on at the chat's place (`loadSkills`). The catalogue rides every agent's instructions in a fixed budget (`skillsSections`), each line with its triggers; a `$<name>` or `/<name>` rides its message whole (`calledNotes`). `SKILL_TOOL` and `skillAnswer` load one, read its folder and search its library; `skillTurningOn` turns one off here on for the chat as its agent loads it. |
| `app/agent/space-dashboard.js` | The space tool's `dashboard` (HarnessV4_AgentsSpace_Plan AS1, AS3): `dashboardCall(input, at, now)` — an agent reads the dashboards its Space shows (`dashboardsWords`, `dashboardWords`, `DASHBOARD_ROWS`), reads a kept one's sources again, pauses one with why (resuming is the person's), and presses a kept one's button on a row, judged by its chat's gate as the button's command would be (`PRESS_READ_ONLY`, `PRESS_FENCED`, `PRESS_MOVED`). services/dashboard-runner.js runs it; the words are here. |
| `app/agent/space.js` | The agents' `space` tool (proposal_ux §4.14), for both engines: a chat's agent reads its project's board and What happened, adds, takes and moves tasks, writes in the logbook (`SPACE_DOOR`); its guided actions (`SPACE_GUIDED`: needs, dashboard, app, lanes, draft, routine, repro) write drafts only the person sends, propose routines and watchers, send a watcher's guidance and say what a repro found. `SPACE_TOOL`, `spaceRun`, `spaceCall`, `spaceGuide`, `spaceProjectOf`, `spaceOffFor`. |
| `app/agent/checkpoint.js` | The checkpoints an agent hears, for every reader: `compose(moment, reader, facts)` → blocks in order, `via` (message, steer, next tool answer), `marks`: the blocks' ids. A reader is what an agent can take (`READERS`), never its brand; `DIVERGENCE` names where the loop and a coding agent differ, and why. Pure: the caller keeps what it said once it reached the agent. A turn's start, a move, a compaction, a call's end, a tick and a note are composed here; a turn's end is each caller's own. |
| `app/agent/stale.js` | The files an agent read that changed since, told as Claude Code tells them: `staleNote(changes, …)`, which turn.js hands the loop as `fileNews` for a turn's first request and each round. Each file of the agent's sightings (hands.js `changedSightings`) whose bytes moved is named with the lines around each change, numbered as it holds them now; a file gone is said gone; at most `STALE_FILE_CHARS` a file and `STALE_NOTE_CHARS` a note. The sighting moves on, so the write guard takes it as read. |
| `app/agent/steer-fork.js` | The forked steer (the owner's of 11-04): `weighAside(…)`, set on a running turn's mailbox, holds a note the person asked a fork for, or every one where the switch is on, out of the loop's reads while a read-only fork weighs it, one at a time — a correction goes in, a question is answered, more work becomes proposed tasks and a sealed letter; none weighed goes straight in, saying why (`steerGate`). `readVerdict`, `letterText`. |
| `app/agent/tool-tail.js` | The tail of Filament's next tool answer (checkpoint.js "tool-answer"): `createToolTails()` — `owe(chain, o)` where a coding agent's turn owes words to an agent that takes them only once a step ended (Cursor's CLI), `take(chain)` as the chat's own agent's next answer from Filament's tools goes (agent-tools.js `tailed`; each judged then, `said` or `dropped`), `drop(chain)` at the turn's end. |
| `app/agent/still-open.js` | What is still open in a chat: its agents' background commands, its coding agent's own background tasks, its sub-agents at work, with work waiting, or failed. `openList`, `stillOpenLines`, `openOf`, `stillOpenOf`, `openWords`, `OPEN_MOST`. The lines ride the block after a summary (sessions/reattach.js); `createStillOpen` keeps what the agent heard (`openHeard`) and tells it again after its own compaction; `alsoOpenWords`: what else is open at a done or tick, new in a turn. |
| `app/agent/skills-back.js` | The skills a coding agent is owed after its own compaction, kept in the chat's meta (`skillsBack`, beside `openHeard`), a restart too: `createSkillsBack({ archive })` — `compacted(chain, who, loaded)` adds what it had loaded to what it is owed still, `loaded` takes one it loaded again, `heard` clears them once the block reached it, `of` reads them. By whose session compacted: the chat's own agent (`CHATS_AGENT`) or a sub-agent's run by its id. Written by acp-turn.js and compactor.js `own`. |
| `app/agent/subagents.js` | Sub-agents (HarnessV3 §15 item 86): `createSubagentRegistry(…)`, one per process — a fresh agent loop on one task, launched by the `agent` tool, the developer or `/subagent`: an `agent/<model>` request served by turn.js in host mode, or a chat on another machine (remote-agents.js; its turn a run here, `mirrorRun`). Foreground or background, followed up in its own context, on the first row that can run; it runs team workers, checks, forks and graph tasks (`launch`, `followUp`, `apply`, `stop`). |
| `app/agent/system.js` | The loop's system prompt in one place (HarnessV3-NewTask NT-D6): `loopSystem(…)` — the request's system text (memory's briefing and the goal), the loop's prompt (prompt.js `systemPromptFor`) with the session's Environment, the instruction files and session text, the skills catalogue, the plugins on and any skill the newest message calls by name, each part apart for the turn's record. The loop sends it and the New Task board weighs it, so the board's figure is the first request's. |
| `app/agent/team-tools.js` | A team's tools (HarnessV3-AtHome P2): the handlers behind its lead's `agent` and `worker` calls, plain JSON in and out, apart from the loop's turn state (turn.js wraps them). `createTeamTools({ registry })` → `{ agent, worker, watch, teamNow }`: launch a worker from a brief (`checkBrief`, `briefText`), message, stop or follow up a worker, watch them run; a lead that reads along has `show_trail`, `show_changes` and `show_report` too. Also `inputRefusal`, `endedWorkers`, `attemptsOf`. |
| `app/agent/thread-tool.js` | The main agent's `thread` tool (app/threads.js): `THREAD_TOOL` (title, brief, model, provider, effort, folder, notify), `threadAtOf` (a harness chat's own agent, its `loop.tools.thread` switch on) and `threadCall`, whose answer names the thread, how its folder was allowed and how to write it; refusals in words. `folderVerdict`, `threadAskWords`, `folderAskOf`: when and how its folder is asked for, on both engines. Never in a team's chat, to a sub-agent or in another machine's agents' chat. |
| `app/agent/tools.js` | The loop's toolset and its permission gate. The hands come from hands.js byte for byte; the loop's own are `ask` (`ASK_TOOL`), `plan`, the graph's `tasks`, `agent`, `wait`, `delegate_read`, the envelope tool and `report`, and a team's lead has its own `agent`, `worker` and `wait` (`leadToolsOf`). Every offered set is a frozen constant chosen once per configuration (`toolSetFor`, `leadToolSetFor`, `loopToolArgs`), never by the mode; `gate`, `ruled` and `permissionQuestion` judge each call. |
| `app/agent/turn-said.js` | What a turn's start says on the person's message (shell exits ahead; hook and change notes, changed files, still open, sealed envelopes, where it stands after): `turnsOf` (each message its own turn's, by the turn's pin, never its words alone), `withSaid`, `putSaidBack`. turn.js keeps them with the turn (`meta.said`, archive `saidOf`, `turnPinsOf`) and puts them back in every later turn, so the history is the bytes the provider cached. |
| `app/agent/workspace-kind.js` | Pure: where a sub-agent works — none, the session's folder, a patch workspace or a worktree — by the launch rules 1–11 of the owner's plan for big repos (`workspaceKind`), and the chat's setting read (`workspaceSetting`, `WORKSPACES`); of which kind its worktree is — full, a clone, sparse (`copyKind`) — and the paths a launch names for a sparse one's cone (`launchPaths`). |
| `app/agent/turn.js` | One client-visible turn of the agent loop: `createAgentLoopTurn(deps)` → `{ turn, close, letGo, symbols }` resolves `agent/<model>` (`parseAgentModel`, `plainModelProblem`) to the loop, whose rounds go back through Filament's front door as ordinary requests while the client sees one reply. A paused turn waits here for the next message (`createParks`, `PAUSE_KINDS`). Sub-agents run here in host mode. Also the folder judgement (`folderVerdict`, `newFolderRefusal`), `loopConfig`, `sessionMode`. |
| `app/agent/visuals.js` | The agent's visuals (HarnessV4_Visuals_Plan E16): a picture it draws with code — SVG or an HTML fragment — shown in a closed frame inside its answer. Two tools of Filament's own for both engines: `VISUAL_GUIDE_TOOL` (`visual_guide`: `visualGuide`, `GUIDE`, `lookRules`) and `SHOW_VISUAL_TOOL` (`show_visual`: `visualOf` checks it, `showVisual` keeps it on its turn and answers that it was shown). `visualWriting` draws it while its call streams; `visualHome`, `visualsKeptOn`, `VISUALS_OFF`. |
