# Module map: ui/harness panels (space, widgets, panes, library, settings)

The [architecture](../ARCHITECTURE.md) explains the layers; each row below says what one file is and does.

## `ui/harness/library/`

| File | What it is |
| ---- | ---------- |
| `ui/harness/library/agents.js` | Library › Agents and teams, `renderLibraryAgents`: one page — the Teams as pods (teams.js), and the Agents (yours first) each with the teams that seat it. A card says what it may do, what it sees, its models first choice first, and its tick "Your agent may use it"; Edit opens editor-sheet.js, a shipped card's changed parts with Put back. Through `/api/agents`; injected `h`, `api`, picker and sheet. |
| `ui/harness/library/editor-sheet.js` | The Library's editors as a sheet over the page: `openEditorSheet` opens an agent's card or a team in a centred glass dialog — its tile and name at the head, parts as inset groups of rows (`part`, `line`), a foot that stays put with why Save waits, Cancel and Save; Esc or × with changes asks first. `shippedMarks` draws a shipped part's "changed", Put back and Take Filament's. Styled in library.css. |
| `ui/harness/library/memory.js` | Library › Memory, `renderMemoryBrowser`: what memory knows — on the left Everywhere and each workspace with counts, on the right the one picked as Memories (the claim browser with Confirm, Correct, Retire, Restore and history), Dossier (its sections with cited claims, Rewrite now), Add, Questions and Models. Live on the bus; `scopeFor` picks the workspace the address names. How memory behaves stays in Settings › Memory. |
| `ui/harness/library/model-list.js` | `modelList`: a list of models, first choice first, as the Library's editors take one — a model picker per row with Take out, a row to add one more up to a most, and `note(name)` under a row saying why that model cannot run now. Used for an agent's models (agents.js) and a team's lead and crew (teams.js); `none` and `next` word the add row. Given `efforts`, each row's effort chip (lib/effort-chip.js), kept by model; `effortsIn`: what a save sends. |
| `ui/harness/library/page.js` | The Library (proposal_ux §4.15) at `#/library/:page`: `LIBRARY` lists its pages — Agents and teams, Skills, Memory, Plugins & Connectors (Artifacts keeps `#/artifacts`); `renderLibrary` draws a full-frame screen over the conversation as Settings is: the crumb "Library › <page>", Back to chat, the title, line and the page. A Settings search result that lives here opens lit; Connectors' address or door opens Plugins & Connectors at its connectors part. |
| `ui/harness/library/plugin-sheet.js` | A plugin's sheet (HarnessV4_SpacesPlugins_Plan B5), `pluginSheet`: its name, version and source; what each part becomes here (`partsList`, `hookWhen`, `runnableHooks`); what is not supported; the values it asks for (`valueFields`, secrets masked); its weight; and where to turn it on — All chats, a Space, a project. Add… installs nothing until its button (`installSteps`); installed, it shows updates, values per place and Uninstall…; `setsUpAt` sends on to a server's setup. |
| `ui/harness/library/plugins.js` | Library › Plugins & Connectors (two pages until 11-09), `renderPlugins`: Connectors (settings/mcp-servers.js; a plugin's connector opens its sheet here), Installed plugins with where each is on, Add from this computer (Claude Code's and Codex's, with Add…), then Find more plugins from the marketplaces as compact cards, two to a row where wide. `connectors`: opened at that part, on a place, with a plugin's setup — where an install with a server over the web goes on. Add… opens plugin-sheet.js. |
| `ui/harness/library/skill-add.js` | Add to skill… (HarnessV4_Skills_Plan step 4), `openAddToSkill`: a standing memory's words written into a skill made in Filament, under the section its kind belongs in (`sectionFor`: Rules, How to work, Facts), shown in place first (`linesFor`, `withLines`, `sectionsOf`); Add re-reads the SKILL.md before writing. `addsToSkill` says which memories offer it; the memory stays. Injected `h`, `api` and dialog. |
| `ui/harness/library/skills.js` | Library › Skills (HarnessV4_Skills_Plan S1-6), `renderSkills`: Always on in picks the place; two sections, always on there and tagged when needed, each skill by its tag with Copy, a switch, ↺ and ⋯; How skills work; a plugin's skills under it; Add skills…, on nowhere. `renderSkillPage` (`#/library/skills/<name>`): a skill's source, files, cost and Books, and Craft it in a chat…; `openNewSkill` makes one. Injected `h`, `api`, menu and dialogs. |
| `ui/harness/library/teams.js` | The Teams part of Library › Agents and teams, `createTeamGroups`: every team as a pod — its lead at the table's head, its crew seated around it — grouped They look and check / They build, with its tick (your agent may start it), Edit, Duplicate, Delete and Put back; the editor in a sheet (editor-sheet.js). `CHECK_DOES`. Each model's agents at once is set on its row under its provider (lib/model-rows.js). |

## `ui/harness/panes/`

| File | What it is |
| ---- | ---------- |
| `ui/harness/panes/agents-band.js` | A sub-agent's copy's parts that the Changes pane draws in the copy's block: `createBand` gives its Apply (said before the press from a dry run, re-read while the pane shows), Mark as applied and Undo, what stops it file by file, Send back to rebase, and its diff (`workOf`, `reread`, `stop`). Buttons are keyed by what they do so a redraw in place (dom.js `morphChildren`) keeps them. `agentsMark` is the mark on the Changes tab while something waits. |
| `ui/harness/panes/artifact.js` | `renderArtifactPane`: an artifact in a side-pane tab of its own (HarnessV4_Artifacts_Plan E18, AF-D35) — a head with its mark, title, version and type, Open full and the arrow to the browser, over its page in a frame (artifact-frame.js). The tab is the artifact's whatever chat is open; its head follows each new version, rename and pin, and a deleted one says so. |
| `ui/harness/panes/browser.js` | The Browser pane (BR4), `renderBrowser` / `refreshBrowser`: the chat's browser — its bar, size chip (`sizeChipWords`, `PAGE_SIZES`), tabs, what the agent does (`lineOf`), Take over, ⋯ with its sites. In the app the page sits over the stage (`bridgeOf`, `covers`); elsewhere it is cast live on the run socket while the stage shows, the person's input reaching it at its own points (`pagePoint`, `CLICK_MS`, `LINE_PX`), else a picture every `SHOT_MS`; none on a view-only page (`setBrowserViewOnly`). |
| `ui/harness/panes/changes-data.js` | The Changes pane's words, pure: `clockOf`, `fileCount`, `workerFile`, `agentName`, `placeKey`, `gitWords` and `GIT_MISSING`, `binaryWords`, `cutWords`, `dirLeaf`, `splitPatch` (a whole diff per file), `DIFF_LINES`; and the repository places' words shared with space/places.js — `placeLine`, `chatsWords`, `chatsTitle`, `placeMenu`, `placeWhy`, `removedLine`, `removedToast`, `goesWords`, `removeSheet`. No DOM, no fetch. |
| `ui/harness/panes/changes-places.js` | The Changes tab by place, pure: `changesModel` shapes `GET /api/git/changes`'s answer with the agents the page holds into a summary line and a block a place — your folder, a sub-agent's copy, another place this chat wrote, then the other chats' worktrees — each with its branch, what sits uncommitted, the agents that wrote there and their files, and the files no agent wrote. `placeFacts`, `copyFacts`, `branchWords`, `subTone`, `subState`, `emptyOf`, `FILES_SHOWN`. |
| `ui/harness/panes/changes.js` | The Changes pane by place, `renderChanges` / `refreshChanges`: one read of `GET /api/git/changes` (shaped by changes-places.js) on open, Read again, a turn's end, sub-agent moves and every `READ_EVERY_MS` while shown; a block a place with its agents and files, a file's diff under its row one at a time, a copy's Apply from agents-band.js (`paintBand`). It only shows: Apply, Send back to rebase and Stop are its actions. `showChanges`, `reviewAgent`. Drawn in place. |
| `ui/harness/panes/code-viewer.js` | The code viewer (§5.9.3), a file's own side-pane tab: `renderCodeViewer` draws a breadcrumb toolbar, a line-numbered pre shiki paints where its grammar knows the extension, the markdown renderer for .md, images on a checker, and the endpoint's refusals in its words; ⋯ holds Wrap lines and the copy paths, Open the editor lib/editors.js picks, where one opens it. `refreshCodeViewer` re-reads it on the pulse, drawing only where it changed; `showLines` opens it scrolled to a tag's lines, marked. |
| `ui/harness/panes/context-how.js` | How earlier turns are kept (HarnessV4_Tasks U3-3): `howSection` draws the section for the chat's sheet and for Settings' defaults — When the chat is full (your line, Then, Back after a break, After an update), How it makes room (the way, who writes summaries), Other agents' results (sealed or whole), History with Undo, and ▸ Advanced. It draws a coding agent's and a client's variants; every write goes through `ctx.write`. `pointLine`. Uses widgets/compaction.js and the ring's `lineControl`. |
| `ui/harness/panes/devtools.js` | Run › For developers' traffic page per session (§5.9.8): `renderDevtools` draws the token-debug tiles and the full table (one row per main-session request: input, output, reasoning, cache read and write, hit rate, TPS), then Network status — each record's upstream attempts with the request headers it kept; response headers are not recorded, and it says so. `refreshDevtools` re-reads it. |
| `ui/harness/panes/files.js` | The Files pane (§5.9.3), `renderFiles` / `refreshFiles`: the project folder as a lazy tree with git-status letters where it is a repository, a filter that falls back to the name search, Show changed files only, and a context menu (Open, Add to chat, Copy path, Show in Changes). A click opens the file as its own code-viewer tab. Redrawn, it keeps open folders and the filter, re-reading a stale tree in place; the last `FOLDERS_KEPT` folders' trees are kept. |
| `ui/harness/panes/last-reply.js` | The newest finished reply's record, in the Run pane: `renderLastReply` heads Run › Calls with what it sent, got back, read from cache and cost, the context sources (§9 B8, an estimate), held tokens per request as a bar chart and a cost forecast only where priced records fund it; `renderFilamentDid` is Run › For developers' "what Filament did to it". `anatomyTurn` picks the reply (mid-turn, the one before). |
| `ui/harness/panes/next-request.js` | The Next request pane (proposal_ux §4.11, M5), `renderNextRequest` / `refreshNextRequest`: what the next message sends — a parts bar from the compose preview (`/compose?dry=1`: Filament's part, the conversation, the draft as typed via `draftMoved`) on the window's scale with the compaction line, and the turns stack (`mapStack`) with the draft as a ghost on top; Dry run shows the request. A coding agent's chat says it builds its own requests. Drawn in place. |
| `ui/harness/panes/outputs.js` | The Outputs pane (HarnessV4_Four_Plan E20), `renderOutputs` / `refreshOutputs`: files the chat's agents wrote that git does not show — outside any repository or git-ignored — newest first, each with its mark (`markOf`) and facts (`rowFacts`, `folderWords`); a row opens the file beside the chat, Show in folder opens the file manager. Gone files fold (`goneWords`); `NOTHING_YET`, `NO_CHAT`, `SNAPSHOTS_OFF`, `COMMANDS_NOTE`. It writes nothing. |
| `ui/harness/panes/pane-buttons.js` | The header's pane buttons (proposal_ux §3.3), `createPaneButtons`: a button per pane given one (`DEFAULT_BUTTONS`: Changes and Terminal until the person picks others, `buttonsOf`), lit while its pane is in front; ⋯ with the other panes, Layout and Show or hide panes; the Layout button named by the arrangement where two columns fit (`layoutItems`, `ARRANGE_WORDS`, `PLACE_WORDS`). One at work out of sight comes out of ⋯ (`works`, `pulledOut`). A press opens or closes a pane, never runs anything. |
| `ui/harness/panes/pane-data.js` | Pure helpers behind the side panes, testable from Node: `statusLetter`, `attemptsOf` (a record's network attempts), `heldOf` / `heldSeries` / `forecastNext`, `promptTagOf`, `ageOf`, `isMainRecord`, `crumbsOf`; the tab ids — `fileTabId`, `fileWhere`, `threadTabId`, `resultTabId` and their parsers — `tabCanOpen` and `closedTabsOf`. |
| `ui/harness/panes/pane-host.js` | The panes beside the chat (proposal_ux §3.5), `createPaneHost`: tiles of tabs laid out by tiles.js, fitted by lib/layout.js — docked in columns or floating as one tile; a tile's head with its pane's controls or tabs, Pop out, ⋯, close; drag via tile-drag.js; thread tabs drawn here. Each chat keeps its own panes (`harness.panes.chats`, the newest 60). Keeps the conductor's contract (`openTab`, `addTab`, `openFileTab`, `openArtifactTab`, `setChat`, `draw`, `pulse`, `refresh`, `setOpen`). |
| `ui/harness/panes/pop-out.js` | Pop out (HarnessV4_BrowserSize_Plan BS4), the page's half: a tile's pane in a window of its own — the harness page showing one tab (`popTabOf` reads `?pane=`) — and the main window's word of which tabs are out (`createPopped` over `popBridgeOf`'s app bridge). `MAIN_LINE` / `mainLine` is the channel between windows; `followable` and `followSwitch` give Follow the main window. Desktop app only. |
| `ui/harness/panes/prompt.js` | Run › Calls (§5.9.6): `renderPrompt` draws one card per model call of the session — collapsed, the record's tag, model, in/out, finish reason and duration; expanded, it fetches the record and shows the input's messages with role stripes and Copy, or a notice where bodies are not stored, and the output's figures. Records are read `RECORD_READS_AT_ONCE` at a time; `refreshPrompt` re-reads. |
| `ui/harness/panes/run-pane.js` | The Run pane (proposal_ux §4.10, M1), `renderRun` / `refreshRun`: this run in three depths under one segmented control (`RUN_PARTS`) — Rounds (run.js), Calls (prompt.js under last-reply.js's record) and For developers (devtools.js and what Filament did). The part shown is the page's; `showRunPart` picks it before a door opens the pane. A coding agent's chat says its own requests do not pass through Filament. |
| `ui/harness/panes/run.js` | Run › Rounds, a run's spine (`renderRunPane`, `refreshRunPane`): one station per round from the run's events with its lamp and what it thought, said and met, and a metrics strip (`renderMetrics`). `stationsFrom` and `stationsFold` are pure; the maximised room (control-room.js) draws the same spine through `renderRun` and `stationsFold`. `compactionWords` says each compaction shape, `windowLine` the window's first line. |
| `ui/harness/panes/team-result.js` | `renderResultPane`: a team's result beside the chat (team_v2_plan §10 O3), opened by Open beside — its head (lead's portrait, team, when it ended, workers), its findings as its lead ranked them (each with where it is, a press opening the file), the unsure ones and what was not covered folded, the whole result as written, and a foot with Send to your agent…, Verify, then send…, Ask its lead. Read once; the foot follows its row in place. |
| `ui/harness/panes/terminal.js` | The Terminal pane (§5.9.9), `renderTerminal` / `refreshTerminal`: real PTY sessions, one xterm each (lib/xterm.js), inner tabs named by title with New terminal and a per-tab kill, "[Process exited]" at the end, and the backlog replayed on attach. Closing the pane leaves terminals running (the status panel lists them with Stop). Every terminal the server holds gets a tab, re-listed past `LIST_MS` on the pulse. A view-only device's page (`setTerminalsViewOnly`): no +, no terminals asked. |
| `ui/harness/panes/thread.js` | `renderThreadPane`: an agent's thread beside the chat (proposal_ux §4.7), one sub-agent's conversation in a tile of its own — the part the Agents tab draws (subagent-viewer.js) with its head, work, changes with Apply and its box; a coding agent's own is read-only. Opened from Open beside and where a saved agent you asked answers while the window has room (app.js `openSubagent`); its tab is the chat's (pane-data.js `threadTabId`). |
| `ui/harness/panes/tile-drag.js` | Moving a pane by hand (proposal_ux §3.5): `dragTab(handle, o)` drags a tab, or a lone pane by its title, onto another tile's tabs to join them or to an edge to tile beside it — pointer events on the window, the landing drawn under the pointer, refused places never offered, Esc or a release off every tile cancels, a press that never moved stays a click. `dropAt` (where a point lands) is pure. |
| `ui/harness/panes/tiles.js` | The panes' layout, pure (proposal_ux §3.5): columns of tiles, each a stack of tabs — `openTab` by the tiling rule (`ARRANGES`, `GRID_ROWS`), `addTab`, `closeTab`, `activate`, `moveTab`, `swapTiles`, `setShares`, `arrange`; `shownOf` cuts the layout to the chat shown and folds it to the room; tabs on top (`toTop`, `fromTop`, `onTop`); `rekey`, `takeChat`, `ownedBy`, `layoutJson` / `readLayout`. pane-host.js draws it; tested in `test/pane-tiles.test.js`. |
